# 架构评审与后续规划（2026-10-16）

依据：当前代码（本地提交 d9d7fca）、STATUS.md、TODO.md、docs/ 下的验证记录。今天是项目设定的截止日。

## 一、架构评价

### 做得好的地方（建议保持）

1. **分层清楚**：数据集 → Runner → Adapter → 证据 → 评分器 → 报告。核心约 1,350 行，Adapter 约 560 行，GUI 约 1,200 行，各层边界清楚。新增一个 Agent 只需要实现 `AgentAdapter` 并注册。
2. **评测可信度的设计到位**：
   - 每个 case 都有独立的临时 home 和工作区；
   - Agent 拿不到 expected；
   - pass、fail、unknown、error、unsupported 五种状态分开统计，缺失的维度不计算总分；
   - 配置、数据、事件和结果都记录 SHA-256；
   - 可以离线重评，不必重跑 Agent。

   openKylin 上 48×2 那次运行的隔离证据（96 个 namespace，reset 后没有残留）说明这些设计确实生效了。
3. **CLI 和 GUI 共用同一个核心**：GUI 通过 `memoryscope ... --json/--jsonl` 子进程调用，不做评分，也不读取密钥，与交接文档的约定一致。CLI 不依赖 Qt。
4. **工程质量**：104 项测试在 Python 3.10 和 3.13 上都通过，失败路径、中断、损坏输入、并发写报告都有覆盖。

### 主要问题（按对作品质量的影响排序）

1. **区分度几乎为零**：96 条结果里 95 条 pass，Codex 97.9 分，dsh 100 分，靠这组数据给两个 Agent 排不出高下。作为 Benchmark，这是最大的实质性短板。根源在于用例偏短、偏直接，而且记忆走的是统一的 `MEMORY.md` 约定，测到的主要是“按约定记笔记、读笔记”的能力。
2. **记忆机制是框架统一规定的，不是产品原生的记忆**：结论只能写成“在统一外部记忆约定下的表现”。目前也没有无记忆基线，无法证明这些题真的必须依赖跨会话记忆才能答对。
3. **评分器存在误判**：唯一的 fail 是 `dynamic_update-007`。Codex 的回答正确，`MEMORY.md` 里写的是“旧值 517 已作废”，却因为出现了 517 这个字符串，被存储检查判为失败。这更像评分规则太严，不像 Agent 的错误。另外，`answer_line` 依赖 Agent 按“答案：”格式作答，格式遵循能力和记忆能力混在了一起。
4. **只跑了一次**：没有重复运行，也没有均值和方差。
5. **数据集还是 draft**：48 条用例数量够了，但没有人工复核。
6. **交付链没在 openKylin 上验证完**：
   - .deb 的安装：桌面系统是 OSTree，/usr 可能只读，验收脚本已经准备了回退到用户目录安装；
   - GUI 依赖的 Qt xcb 系统库（例如 libxcb-cursor0）是否齐全；
   - `setup_openkylin.sh` 整体跑通。

   以上目前都只在 macOS 上验证过。另外，带上 PySide6 之后 .deb 有 130 MB。
7. **GUI 层**：`app.py` 一个文件 956 行，作为 MVP 可以接受，截止后再拆分。`memoryscope view` 生成的 HTML 页和 GUI 是两套展示代码，以 GUI 为主，HTML 页只作为没有 Qt 时的备用。
8. **文档分散且有矛盾**：PROJECT_SPEC、IMPLEMENTATION_PLAN、ARCHITECTURE_REVIEW（10-13）、STATUS、TODO 里有过期的表述，比如虚拟机是 Server 还是 Desktop，以及“GUI 待实现”。提交前需要统一。比赛规则（截止时间、提交方式）也还没从官方来源核实完。
